@AGENTS.md

Urvar CRM — internal CRM for Urvar Natural Pvt Ltd (organic fertilizers/bio-fertilizers B2B/B2C). See [README.md](README.md) for tech stack, setup, demo accounts, and project structure — don't duplicate that here.

## Architecture Rules

- **Prisma 7, custom client output.** The generator (`prisma/schema.prisma`) writes to `src/generated/prisma` (gitignored), not `node_modules/.prisma`. Import enums/types from `@/generated/prisma/...` (e.g. `@/generated/prisma/enums`), not `@prisma/client`. Run `npm run db:generate` after editing the schema.
- **Datasource URL lives in `prisma.config.ts`**, not the `datasource` block in `schema.prisma` — it still reads `DATABASE_URL` from `.env`.
- **RBAC is enforced in application code, not middleware.** `middleware.ts` only redirects unauthenticated requests to `/login`. Every Server Action / route handler that touches CRM data must call `can()` / `assertCan()` and scope its Prisma `where` with `scopeWhere()` (all in `src/lib/permissions.ts`). Scope is one of `none` / `own` / `territory` / `all` per (role, module, action) — adding a module or action means updating the `PERMISSIONS` matrix for all 5 roles, not just the one being tested.
- **Always combine `scopeWhere()` with request-controlled filters via `AND`, never a spread.** Build `where = { AND: [scopeWhere(...), filters] }` — spreading `scopeWhere(...)` and then setting a sibling key (e.g. `where.state = params.state`) is a plain JS object-key collision that silently overwrites the scope restriction instead of erroring. Prisma ANDs duplicate keys across array elements rather than one overwriting the other, so a conflicting param returns zero rows instead of leaked ones. Apply this to any page/action that combines `scopeWhere()` with request-controlled filters.
- **Phone numbers are stored as plain 10-digit Indian mobile numbers** (see `src/lib/validations/lead.ts`, `customer.ts`). Only convert to E.164 at the Plivo dial boundary via `toE164()` in `src/lib/phone.ts` — don't normalize on save.
- **Local file storage, not cloud.** Call recordings and uploaded documents live under `storage/` (gitignored; base paths are `CALL_RECORDINGS_DIR`/`DOCUMENTS_DIR` in `.env`), named by the DB row's cuid — never by a user-supplied filename, so a crafted name can't escape the directory. Read routes (e.g. `src/app/api/documents/[fileId]/route.ts`) are **deny-by-default**: authorize the database row via `scopeWhere` on the related record before reading any bytes.
- **Windows box, no Docker/WSL, Postgres is a real Windows service.** `postgresql-x64-18` runs Automatic on `localhost:5432` — no manual start/stop needed, ever. Don't assume `psql`/`pg_ctl` are on PATH.
- **This same machine also runs production** (crm.urvarindia.com), alongside three sibling apps (`urvar-hr`/`urvar-erp`/`urvar-website`) — all managed by **PM2**, not Windows services or WinSW. `D:\urvar-crm\ecosystem.config.js` defines the `urvar-crm` PM2 process (`next start -p 3002`; ports 3000/3001/3002/3003 are hr/erp/crm/website respectively). PM2 runs as an Automatic Windows service, so `pm2 save`d processes auto-resurrect on reboot. Cloudflare Tunnel routing (`crm.urvarindia.com` → `localhost:3002`) is its own separate Windows service, `CloudflaredCRM`, mirroring the sibling `Cloudflared`/`CloudflaredERP`/`CloudflaredWebsite` services exactly (each a raw Windows service invoking `cloudflared.exe --config=<path> tunnel run`, not `cloudflared service install`). Any new Cloudflare Tunnel service needs crash-recovery set explicitly — `sc.exe failure <name> reset= 86400 actions= restart/20000` — since `New-Service`/`sc.exe create` doesn't configure it by default. **Nightly DB backup** (Phase 0 of the sales-funnel automation roadmap, `all.md`) runs via the Windows Scheduled Task `UrvarCrmDbBackup` (daily 02:00, `scripts/backup-db.ps1`, `pg_dump -Fc` to `D:\Backups\urvar-crm\`, 14-day retention) — registered and confirmed working via a manual `schtasks /run`. Restore (`scripts/restore-db.ps1`, defaults to a disposable `urvar_crm_restore_test` target) needs the `postgres` superuser role (the app's own `urvar_app` DB user lacks `CREATEDB`, same root cause as the `prisma migrate dev` P3014 issue below) — live-test it before trusting it in an emergency.
- **Deploy flow**: `npm run db:generate && npx prisma migrate deploy && npm run build && pm2 restart urvar-crm` — no elevated shell needed; elevation is only needed for Cloudflare Tunnel service changes (rare, one-time setup already done).
- **There is no separate dev database.** `DATABASE_URL` in `.env` points at the same `urvar_crm` database on `localhost:5432` that production reads from. Run `npx prisma migrate status` before `prisma migrate dev` to confirm there's no drift (a drift-triggered reset prompt would wipe production data); additive nullable-column migrations are low-risk but still real production schema changes, not throwaway dev ones.
- **`prisma migrate dev` does not work on this box** — the DB user lacks `CREATE DATABASE`, so the shadow database fails with `P3014`. To add a migration: edit `schema.prisma`, run `npx prisma migrate status` (confirm no drift), generate the SQL with `npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script -o prisma/migrations/<timestamp>_<name>/migration.sql`, **read it and confirm it contains no `DROP`/`TRUNCATE`**, then apply with `npx prisma migrate deploy` and `npm run db:generate`. Note the flag name: `--from-schema-datasource` was removed in Prisma 7 in favour of `--from-config-datasource`.
- **Local dev on this box can't use ports 3000-3003 or a `.env.local` file.** Those four ports are taken by the four PM2-hosted apps (hr/erp/crm/website) — run `next dev` on something else (e.g. `PORT=3005`). `.env`'s `NEXT_PUBLIC_APP_URL`/`BETTER_AUTH_URL` are hardcoded to `https://crm.urvarindia.com`, so better-auth's client will try to hit production unless overridden — pass `NEXT_PUBLIC_APP_URL`/`BETTER_AUTH_URL` as shell env vars on the `npm run dev` command itself (they take precedence over `.env`). Don't create a `.env.local` to do this instead: the `urvar-crm` PM2 process runs `next start` from this exact same `D:\urvar-crm` working directory, so a stray `.env.local` would silently override production's auth URLs on its next restart too. Also stop the local dev server before running `npm run build` for a real deploy — `next dev` and `next build` share the same `.next` directory and can conflict if run concurrently.
- **Better-auth user email/password are edited directly via Prisma, not the admin plugin.** `src/app/(dashboard)/users/actions.ts` updates `User.email` directly and, for password resets, hashes the new password with `hashPassword` from `better-auth/crypto` and writes it to the user's `Account` row (`providerId: "credential"`, upserted) — this matches what better-auth's own `admin.setUserPassword` endpoint does internally, without pulling in the full `admin` plugin. Never log the plaintext password to the audit trail — log a `passwordChanged: true` flag instead.
- **Customers can be pinned to an exact map location.** `Customer.latitude`/`longitude` (nullable `Float`) are set via a Leaflet + OpenStreetMap dialog (`customers/[customerId]/location-dialog.tsx` + `location-map.tsx`, dynamically imported with `ssr: false`) — no API key/billing since it's OSM tiles, not Google Maps.
- **Calling works from both Leads and Customers.** `initiateCall`/`logCall` (`src/app/(dashboard)/calls/voice-actions.ts`, `actions.ts`) take a `{ leadId } | { customerId }` discriminated union, not a bare id. The `Call` model has both FKs; the global `/calls` list joins both `lead` and `customer` and links to whichever is set.
- **Calling is Plivo-based** (Indian caller ID; Twilio was never actually live and is kept only as a historical `CallProvider` enum value). `src/lib/plivo.ts`, `src/app/api/voice/plivo/{answer,status,recording,transfer}/route.ts`, `src/lib/call-recordings.ts`, `src/lib/crypto.ts` (AES-256-GCM at-rest encryption via `ENCRYPTION_KEY`), and `CallProvider.tsx` (`plivo-browser-sdk`'s `Client`, event-driven) implement it. Per-user Plivo SIP **Endpoint** credentials (`User.plivoEndpointId`/`plivoUsername`/`plivoPasswordEncrypted`) are created lazily on first call and are persistent, password encrypted at rest.
- **The AI voice agent's conversation LLM is provider-swappable.** `voice-agent/pipeline/llm-provider.ts` is the only place that knows how OpenAI and Sarvam differ (auth header vs bearer token, `reasoning_effort` support, `max_tokens` vs `max_completion_tokens`). Switch with `VOICE_AGENT_LLM_PROVIDER=openai|sarvam` plus `pm2 restart urvar-voice-agent` — no rebuild needed.
- **Voice-agent conversation quality is mostly prompt and pacing, not the model.** TTS is sentence-chunked, never clause-chunked. `clearAudio` must fire only on a genuine barge-in. Because `end_call` compliance is unreliable on both providers, `server.ts` also enforces server-side wrap-up: silence timeout and a hard duration cap.
- **The voice agent's qualifying question branches on `Lead.customerType`** (shown in the prompt as "Segment", labelled via `CUSTOMER_TYPE_LABELS`) instead of assuming every lead is a farmer — a farmer gets asked about land/crops, a dealer/distributor about volume handled and brands carried, an FPO/NGO about member count, etc. (`voice-agent/pipeline/openai-agent.ts`, `buildSystemPrompt`'s call-flow step 3). A clear buying signal (e.g. a trade buyer asking for a price list) must always override this scripted question and go straight to `transfer_to_human` — the prompt says so explicitly, because the segment question otherwise reads as more salient to the model than the transfer rule.
- **Sarvam document intelligence (`src/lib/sarvam-vision.ts`) powers all document intake.** Use the **extract** endpoint (`POST /doc-ai/v1/job/extract`), not digitise — it's a job queue (submit, poll status, fetch results) and the `schema` field must be a real JSON Schema object. Hard limits on every tier including Enterprise: 10 requests/minute, 10 pages per PDF, 200 MB.
- **Extraction never writes to a record directly.** Lead capture from a document (`leads/import`) converges on the existing spreadsheet importer so it gets the same duplicate-phone detection and Zod validation for free. Attach-and-extract on a lead (`leads/[leadId]/document-actions.ts`) proposes changes the rep ticks, with `name`/`phone` deliberately not extractable, and the accepted payload filtered against a server-side whitelist rather than trusted.
- **Procurement (`/purchases`) is the only inbound side of the schema.** `Supplier` / `PurchaseInvoice` / `PurchaseInvoiceItem` exist so a scanned supplier invoice has somewhere to land; everything else in the CRM is outbound (`Quotation → Order`). `PurchaseInvoiceItem.productId` is optional, unlike `QuotationItem.productId`. The `purchases` module is `NONE` for all three sales roles and full only for `SUPER_ADMIN`/`ACCOUNTS_TEAM`, because supplier prices reveal margin. `@@unique([supplierId, invoiceNumber])` catches the same invoice being photographed twice.
- **Outbound email is SMTP via Zoho Mail** (`info@urvarindia.com`, Mail Lite plan), sent through `src/lib/email.ts`'s provider-agnostic `sendEmail()` — any SMTP account works by filling in `SMTP_HOST`/`PORT`/`USER`/`PASS`/`FROM`. `isEmailConfigured()` gates every call site, so a blank `SMTP_HOST`/`SMTP_FROM` makes sending a silent no-op rather than an error. Two callers: `src/lib/quotation-notify.ts` (`notifyQuotationSent`, fired from `updateQuotationStatus` when a quotation moves to `SENT` — renders the PDF, emails it with the sending rep's own address as Reply-To, and best-effort attempts WhatsApp via `src/lib/whatsapp.ts`) and `src/lib/reminder-cron.ts` (see below). Every attempt, success or failure, is written to `MessageLog` (`purpose: QUOTATION_SENT`) so "did the customer ever get it" doesn't depend on Zoho's own dashboard.
- **WhatsApp quotation delivery exists in code but ships switched off.** `src/lib/whatsapp.ts` sends via Plivo (already a Meta Solution Provider for voice, so no new credentials) but needs a WABA + a Meta-approved template — a manual multi-day step outside this codebase — before `WHATSAPP_ENABLED=true` does anything. Register the template under Meta's **Utility** category, not Marketing (transactional, ~Rs 0.13/msg vs ~Rs 0.95/msg). Flipping the flag is a `pm2 restart`, not a rebuild.
- **Follow-up/task due reminders run on an in-process cron**, not a Windows Task Scheduler job. `instrumentation.ts`'s `register()` hook (Next calls it once per server boot) imports and calls `registerReminderCron()` (`src/lib/reminder-cron.ts`), which schedules a `node-cron` sweep every 15 minutes (`noOverlap: true`, so a slow sweep can't double-send). Safe as a single in-process job only because this app runs as one `next start` process under PM2 — scaling to multiple instances would turn the `reminderSentAt` guard into a race. `reminderSentAt` is stamped whether or not the email send succeeds — the in-app notification (`notifySystem()` in `src/lib/notifications.ts`, deliberately not routed through `notifyUser()`'s self-notification guard) has already landed, and a dead mail server shouldn't mean re-reminding the same item every 15 minutes forever.
- **The sales-funnel automation phases each ship behind their own fail-closed flag** (see `all.md` in `~/.claude/plans/`). Live already: the reminder cron's quotation-chase and stale-lead escalation sweeps, the `SENT`-side pipeline sync in `updateQuotationStatus()`, `src/lib/safe-zone.ts`'s read-only classifier, and the Neo4j graph enrichment. Built but **off by default**, each a `.env` edit plus `pm2 restart` (no rebuild): `AI_AUTO_QUOTE_ENABLED` (the voice agent's `create_quotation`), `QUOTATION_ACCEPT_LINK_ENABLED` (the customer accept-link), `AI_OUTBOUND_BACKLOG_ENABLED` (the backlog dialer). These check `=== "true"` — deliberately the opposite of `AI_TRANSFER_ENABLED`'s fail-open `=== "false"`, because each writes something customer-facing with no human in the loop.
- **A customer can accept a quotation without a rep** (`src/app/api/quotations/accept/[token]/route.ts`), which creates the `Order` directly. It lives under `/api/` on purpose: `middleware.ts`'s matcher excludes only `/api/**`, so that is the one place an unauthenticated customer can reach. `Quotation.acceptToken` (nullable, unique, `src/lib/tokens.ts`) is minted on the `SENT` transition and is the entire authorization — **`GET` only renders, `POST` does the write**, because email security scanners prefetch links and would otherwise accept quotations on the customer's behalf. Not-found and already-processed render byte-identically so a guessed token can't probe state. No `ACCEPTED`-side pipeline sync here, for the same unresolved `ORDER_RECEIVED`/`WON` ordering reason commented in `quotations/actions.ts`.
- **The AI outbound backlog sweep (`src/lib/ai-backlog-cron.ts`) must not be enabled without legal sign-off** on TRAI DND exposure — it autonomously dials real people. Quiet hours are enforced by the cron expression itself (`0,30 10-18 * * *`, `Asia/Kolkata`) rather than a runtime clock check, so nothing can even be scheduled outside business hours. Eligibility is `calls: { none: {} }` — a lead that has ever been called is permanently excluded, which also self-guards against re-dialing across ticks. The dialing itself lives in `src/lib/ai-call-dialer.ts`'s `dialAiCall()`, shared with `initiateAiCall()`; only that action does the scoped RBAC check, since the cron has no session.
- **Field visits (`/field-visits`) are a rep's GPS-stamped check-in/check-out against a lead or customer**, captured from the browser's Geolocation API (`src/lib/geolocation.ts`, `enableHighAccuracy: true`, `maximumAge: 0` — a cached fix from earlier in the day is exactly wrong for a check-in). `FieldVisit.checkInLat/Lng` is where the rep *was*, distinct from `Customer.latitude/longitude` (where the shop *is*). At most one open visit (`checkOutAt: null`) per rep, enforced in `checkIn()` (`field-visits/actions.ts`), not by a DB constraint. An optional check-in photo goes through `assertPhotoUploadAllowed()` (`src/lib/documents.ts`, JPG/PNG only, 10MB cap) — a separate limit from the Sarvam-bound document uploads, since these photos never reach Sarvam.
- **Shared `DialogContent` (`src/components/ui/dialog.tsx`) is capped `max-h-[85vh]`** with an inner `overflow-y-auto` wrapper around `{children}`; the close (✕) button stays a sibling *outside* that wrapper so it doesn't scroll away with the form.
- **The real Urvar logo lives at `public/urvar-icon.png`** (mirrored at `src/app/icon.png`, baked into `src/app/favicon.ico`). If Urvar issues a brand refresh, re-pull from `urvarindia.com` (their CDN 403s a bare `WebFetch`/no-UA request — use `curl` with a real browser `User-Agent`); the full vertical wordmark lockup is at `/logo.png` and `/logo.svg` there, distinct from the square icon.

## Naming Conventions

- **Pages/layouts**: standard Next.js `page.tsx` / `layout.tsx` in every route folder. Dynamic segments use `[camelCaseId]` (`[leadId]`, `[customerId]`, `[quotationId]`, `[fileId]`, `[recordingSid]`).
- **Server Actions**: always `actions.ts` per module/subfolder; domain-specific variants get a prefix (`voice-actions.ts`, `ai-voice-actions.ts`, `document-actions.ts`, `status-actions.tsx` — `.tsx` only when the file exports JSX). Import wizards get their own `import/actions.ts`.
- **Components**: kebab-case filenames even though exports are PascalCase — `product-form-dialog.tsx`, `mobile-nav-drawer.tsx`, `schedule-follow-up-dialog.tsx`, `dropdown-menu.tsx`.
- **Validation schemas**: one file per domain entity in `src/lib/validations/`, lowercase singular noun, no separators — `lead.ts`, `customer.ts`, `product.ts`, `quotation.ts`.
- **`lib/` utilities**: kebab-case for multi-word files (`call-recordings.ts`, `customer-import.ts`, `lead-document-extract.ts`, `quotation-notify.ts`, `reminder-cron.ts`), plain lowercase for single-word (`auth.ts`, `prisma.ts`, `phone.ts`, `crypto.ts`, `email.ts`, `whatsapp.ts`, `geolocation.ts`). Subfolders: `validations/`, `constants/`, `pdf/`.
- **Prisma models**: PascalCase singular (`Lead`, `Customer`, `Product`, `QuotationItem`, `PurchaseInvoiceItem`, `Supplier`, `File`, `MessageLog`, `FieldVisit`). **Enums**: PascalCase, domain-suffixed (`LeadStatus`, `CallOutcome`, `PipelineStage`, `TaskPriority`, `QuotationStatus`, `MessagePurpose`, `MessageDeliveryStatus`).
- **API routes** (`src/app/api/**/route.ts`): folder-per-resource; import flows get nested `import/parse`, `import/template` subfolders; voice endpoints are grouped under `api/voice/plivo/{ai-answer,answer,recording,status,transfer}/route.ts` and `api/voice/{recordings/[recordingSid],token}/route.ts`.
- **`voice-agent/`**: kebab-case pipeline-stage files under `pipeline/` (`sarvam-stt.ts`, `sarvam-tts.ts`, `llm-provider.ts`, `openai-agent.ts`, `turn-metrics.ts`, `backchannel.ts`); `tools/crm-tools.ts`; verb-noun scripts under `scripts/` matching their `package.json` script name (`eval-agent.ts`, `latency-report.ts`, `transcript-stats.ts`, `tts-samples.ts`).

## Test Expectations

- **No automated test suite.** No `*.test.ts`/`*.spec.ts` files or `__tests__` directories anywhere, and no jest/vitest/playwright config. Validate every change with `npm run lint` and `npm run build` (type-checks via `tsc`), plus manual testing through `npm run dev`.
- **Targeted harnesses exist for the voice agent** (evaluation tooling, not a test framework): `npm run eval:agent` replays 21 scripted multi-turn calls across Bengali/Hindi/English through the real system prompt and CRM tool schemas (tool execution stubbed — never writes to the DB), scores both LLM providers, and exits non-zero on any failed check so it can gate a deploy (`EVAL_REPORT=path.json` for a machine-readable report). A provider timeout counts as a stall, not a failed check. **Run `eval:agent` after any change to the agent prompt or tools.**
- `npm run voice:stats` measures how the agent actually talks (turn length, question-stacking, talk ratio) from stored transcripts.
- `npm run voice:latency` summarizes the `[turn]`/`[call-metrics]` telemetry lines into p50/p90.
- `npm run tts:samples` renders the same line across speakers/pace/preprocessing into `storage/voice-samples/` for a human to listen to.

## Known Gotchas

- **Plivo `<Record>` needs `callbackUrl`, not just `action`.** With `startOnDialAnswer: "true"`, Plivo sends the initial `RecordingDuration: "-1"` ping to `action` but delivers the real completion payload (actual `RecordUrl`/`RecordingID`/duration) only to `callbackUrl`. `src/app/api/voice/plivo/recording/route.ts` leaves `recordingUrl`/`recordingSid` `null` on a failed local download rather than falling back to the raw external Plivo URL (which the UI's `startsWith("/api/voice/recordings/")` check would then hide with no visible error). Recording download Basic Auth is off by default in Plivo — enable it in Console > Voice > Other Voice Settings before relying on it being enforced.
- **The Dial-level status callback carrying our `callId` uses `DialBLegStatus`/`DialBLegDuration`, not `CallStatus`/`CallDuration`** — those only exist on the separate Application-level Hangup URL hit, which has no `callId` and is correctly 400'd.
- **Plivo Endpoint `alias` rejects spaces** (use `.`/`+`/`@`/`-`/`_` only); **`username` must be ≤25 chars, strictly alphanumeric**, and Plivo can silently mangle a requested username — always store the API response's `username`, never the locally-generated value.
- **`plivo-browser-sdk` references `window` at module load** — `CallProvider.tsx` must dynamic-`import()` it inside a client-only `useEffect`, never as a static top-level import, or SSR crashes.
- **An Endpoint-originated call's `Direction`/`CallDirection` reports `"inbound"`** (documented Plivo quirk) — don't gate authorization on it.
- **`end_call` used to be the only thing that wrote `Call.outcome`.** `voice-agent/server.ts`'s `finalizeSession` now records a default outcome (`CONNECTED`, or `TRANSFERRED_TO_HUMAN` after a handoff) plus a follow-up task whenever `end_call` never fired, via `recordCallOutcome()` shared with the tool's own `end_call` branch. `transcript` and the AI summary are written as two independent Prisma updates so a slow/failed summarizer can't destroy the transcript.
- **`transfer_to_human`'s route and tool-execution case always worked, but the tool schema was missing from `CRM_TOOLS`** — the model could never call it regardless of prompt. `AI_TRANSFER_ENABLED=false` withdraws it again without a deploy.
- **The AI call's audio shares a Cloudflare Tunnel with the CRM website.** `Call.aiMetrics` records inbound frame inter-arrival `frameGapP50/P90/Max` and `longGaps` per call. Decision trigger, not yet crossed: if `frameGapP90` exceeds ~200ms, or gaps over 500ms show up on more than ~5% of calls, split `voice.urvarindia.com` onto its own cloudflared service.
- **Barge-in is two-stage**: hold new TTS audio on speech onset, commit (`clearAudio`, cancel the turn) once a partial transcript proves it's real speech, resume the held audio if it was noise or a backchannel. Revert with `VOICE_AGENT_BARGE_IN=final-only`. The backchannel matcher (`pipeline/backchannel.ts`) must keep `\p{M}` when stripping punctuation or Bengali/Devanagari entries silently fail to match.
- **A lone STT final can be half an answer, not all of it.** Sarvam's server-side VAD (`silence_duration_ms=300`) finalizes on any 300ms pause, so a lead who pauses mid-sentence (found live: "Amra" ... "Harmicompost", split by a beat while recalling the English word) gets two separate finals instead of one — the old code dispatched each as its own turn, so the model answered the first fragment alone and re-asked its own question verbatim. `server.ts`'s `dispatchOrCoalesce()` holds a lone, non-backchannel single-word final for `FRAGMENT_COALESCE_MS` (600ms, tunable via `VOICE_AGENT_COALESCE_MS`) and merges a fragment that lands in that window instead of firing a second turn; `looksLikeFragment()` deliberately only catches single-word non-backchannel text so normal short answers ("6 ton", "15 tarikh") dispatch with no added delay. The existing busy-turn queue (`pendingUtterance`) still keeps only the most recent utterance on purpose (a separate past fix for stale queued utterances) — deliberately not touched by this one. The system prompt (`pipeline/openai-agent.ts`) also has a standing rule not to re-ask verbatim when a reply looks like a cut-off fragment, as a second line of defense for gaps wider than the hold window.
- **Sarvam TTS needs `speech_sample_rate` (not `target_sample_rate` — a wrong key is silently ignored and defaults to 24kHz)**, `language_code` is required with no "auto", and needs an explicit `flush` after the last utterance of a turn.
- **The model writes the right language in the wrong script, and a `bn-IN` voice reading Latin letters is what "robotic Hindi-sounding Bengali" actually is.** Found 2026-09-19: language resolution was correct on all four calls (`TTS language=bn-IN (source=state...)`) while the model wrote romanized Bengali ("Apnar jomir poriman ar ki chash koren?"). Per-call Bengali-script vs Latin utterance counts were 21/0, 45/0, 1/0, then 7/24 — intermittent, and self-sustaining once started, because the romanized history keeps the next turn romanized. The prompt now names the script AND stopped demonstrating romanization in its own examples; `pipeline/script-guard.ts` is the deterministic backstop. It runs **alongside** the speech, not in front of it: the sentence is spoken as written and the converted text is patched into the assistant turn in `agentHistory` a moment later, because the Sarvam `/transliterate` hop measured 524-875ms per sentence (a 600ms timeout made it inert while its logs looked healthy — the numbers are recorded in the file). That ordering is deliberate and is the whole design: drift does not recur randomly, it recurs because a romanized assistant turn is sitting in the history, so fixing the history fixes the call while costing the caller nothing. One turn can still be heard romanized. `needsTransliteration()` is local and free, and skips anything that reads as English (a function-word count), so a deliberate English reply survives the window before the voice switches. `RESTORE_LATIN` puts the company name back into Latin afterwards, because Sarvam renders "Urvar Natural" as a Bengali word meaning "fertile" and mispronounces the brand.
- **A filler word is a latency cover, not a personality.** `fillerWord()` must be indexed by a counter that advances once per *filler* (`session.fillerSeq`), never `utteranceSeq` — every streamed sentence, closing line and holding line bumps that one too, so the documented cycle never happened and one word came up 47 times in a single log. It also takes the previous filler and steps past it. Separately, the server's filler and the model's own opening reaction collided on 44 logged turns ("হ্যাঁ..." then "হ্যাঁ দাদা, ..."); `stripLeadingAcknowledgement()` in `pipeline/backchannel.ts` removes the duplicate, first sentence of a turn only, and only when a filler actually played. `FILLER_DELAY_MS` is 600ms, not 400 — 400 sits inside the model's normal 350-450ms time to first sentence, which is why fillers were 26.5% of everything the agent said.
- **Server-spoken lines must come from `pipeline/tts-language.ts`'s `PHRASES` table, never a string literal in `server.ts`.** The stall line was hardcoded Hindi ("Sorry, ek minute. Main check kar raha hoon.") and the tool-hop-exhausted fallback was hardcoded English; both were read out mid-way through Bengali calls. `fillerWord`/`closingLine`/`holdingLine`/`fallbackLine` all key off `session.languageCode`.
- **`Product` holds four active rows, all with `mrp` 0** — Enriched Vermicompost, Phosphate Rich Organic Manure, Liquid Humic Acid and Cow Dung Manure [FYM] — so the `mrp`-0 guard turns every one of them into `priceOnRequest` and the agent still cannot quote a price to anyone. `nutrientContent`/`problemSolved`/`description` are filled from the knowledge graph by `npm run db:enrich-products` (`scripts/enrich-products-from-graph.ts`, dry-run by default, explicit sku->graph-id map, never fuzzy-matched); `dosage` and `applicationMethod` are absent from the graph too and need an agronomist. The graph knows 8 products against the CRM's 4, and `graphFacts()` filters its product names against the CRM catalogue so the prompt cannot name something we do not stock. Loading real prices is a data task, but it gates most of the voice agent's usefulness — check this before concluding an agent answer is a prompt bug.
- **`Lead.cropInterest` is free text that in practice lists several crops** ("Paddy, Wheat, Tomato, Brinjal"). `graph-facts.ts`'s `matchCrops()` tokenizes on `,` `;` `/` `&` and "and" before matching — an earlier version slugged the whole string into one nonsense id and silently matched nothing, costing every multi-crop lead its enrichment while the district half kept working (so it looked healthy). Capped at `MAX_CROPS` (3), first-mentioned first, matched in one `UNWIND` query, and facts are crop-attributed so the agent knows which product belongs to which crop.
- **Neo4j lookups go cold with idleness, not just process age.** A one-shot boot warm-up was tried first and was not enough: the connection sat idle a few minutes and the very next call's two lookups both blew the 1500ms budget, silently degrading to no facts (`graph facts resolved: 0 product(s), district=no match`). `startKeepAlive()` in `voice-agent/lib/neo4j.ts` now pings every 60s with a query touching the same labels the real lookups use — `verifyConnectivity()` alone was insufficient, the connection was live and the next query still timed out. It logs only on health transitions. When debugging missing enrichment, note `runReadQuery` masks a timeout as an empty result, so "no match" and "timed out" look identical from the outside — check for `[neo4j] query failed` lines, and confirm the line number in the stack trace matches the *current* file before assuming an error is recent.
- **The product catalogue previously had no agronomy data.** `Product` has 8 nullable agronomy columns (`targetCrops`, `problemSolved`, `dosage`, `applicationMethod`, `nutrientContent`, `benefits`, `objectionNotes`, `availability`); a blank field should make the agent offer a callback, never guess. The catalogue is preloaded into the system prompt at call start rather than fetched mid-call, since a price question used to cost a full tool round trip at the highest-intent moment in the call.
- **README's "Build Roadmap"/"Status" section can drift stale** — confirm what's actually implemented by reading the code, not the doc.
- **A quotation-creation/send tool exists for the voice agent but is dark by default** (Phase 5 of the sales-funnel automation roadmap) — `voice-agent/tools/quotation-tool.ts`'s `create_quotation`, gated behind `AI_AUTO_QUOTE_ENABLED` (fail-closed, `=== "true"`, deliberately unlike `AI_TRANSFER_ENABLED`'s fail-open convention — see that file's comments). Only fires for an existing customer's simple standard reorder inside the Phase-4 safe zone (`src/lib/safe-zone.ts`'s `classifyQuotationSafeZone`, checked server-side, never trusted from the model). While the flag is off, `crm-tools.ts`'s `check_quotation_status` (reads an existing quotation's status) is the only quotation-related tool, and the prompt must never let the agent promise to send or prepare a quotation itself — it tells the lead a sales rep will do that and calls `schedule_follow_up` instead, same "don't promise a capability that doesn't exist" pattern as `transfer_to_human`'s fallback.
- **A stale `.next` build masquerades as a code bug.** If `crm.urvarindia.com` shows Next's generic "This page couldn't load" screen site-wide (not just one route) and the browser console has `ChunkLoadError: Failed to load chunk .../<hash>.js`, it means `npm run build` ran without a following `pm2 restart urvar-crm` — the running `next start` process is still serving HTML that points at chunk files the new build already deleted. Nothing shows up server-side because the failure is a static-asset 404/500 in the browser. Diagnose by comparing `.next/BUILD_ID`'s mtime against the PM2 process start time before reading any page code; fix is the restart (which also means whatever was compiled into that `.next` — including uncommitted work — goes live, so check `git status` first).
- **`.env` changes need a `pm2 restart`, but not `--update-env`.** `ecosystem.config.js` only injects `NODE_ENV` into the PM2-tracked env; everything else (`SMTP_*`, `PLIVO_*`, etc.) is read straight off disk by Next's own env loader (`@next/env`) at process boot. Any restart re-execs `next start` and re-reads `.env` from scratch — `--update-env` is only needed for variables PM2 itself injected via `ecosystem.config.js`'s `env` block.
