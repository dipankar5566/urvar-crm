Urvar CRM — internal CRM for Urvar Natural Pvt Ltd (organic fertilizers/bio-fertilizers B2B/B2C). See [README.md](README.md) for tech stack, setup, demo accounts, and project structure — don't duplicate that here.

## Repo-specific conventions

- **Prisma 7, custom client output.** The generator (`prisma/schema.prisma`) writes to `src/generated/prisma` (gitignored), not `node_modules/.prisma`. Import enums/types from `@/generated/prisma/...` (e.g. `@/generated/prisma/enums`), not `@prisma/client`. Run `npm run db:generate` after editing the schema.
- **Datasource URL lives in `prisma.config.ts`**, not the `datasource` block in `schema.prisma` — it still reads `DATABASE_URL` from `.env`.
- **RBAC is enforced in application code, not middleware.** `middleware.ts` only redirects unauthenticated requests to `/login`. Every Server Action / route handler that touches CRM data must call `can()` / `assertCan()` and scope its Prisma `where` with `scopeWhere()` (all in `src/lib/permissions.ts`). Scope is one of `none` / `own` / `territory` / `all` per (role, module, action) — adding a module or action means updating the `PERMISSIONS` matrix for all 5 roles, not just the one being tested.
- **Phone numbers are stored as plain 10-digit Indian mobile numbers** (see `src/lib/validations/lead.ts`, `customer.ts`). Only convert to E.164 at the Twilio dial boundary via `toE164()` in `src/lib/phone.ts` — don't normalize on save.
- **Local file storage, not cloud.** Call recordings and other generated files live under `storage/` (gitignored; base path is `CALL_RECORDINGS_DIR` in `.env`).
- **Windows box, no Docker/WSL, Postgres is a real Windows service.** `postgresql-x64-18` runs Automatic on `localhost:5432` — no manual start/stop needed, ever (the old `npm run pg:start`/`pg:stop`/portable-Postgres setup was stale and has been removed). Don't assume `psql`/`pg_ctl` are on PATH.
- **This same machine also runs production** (crm.urvarindia.com), alongside three sibling apps (`urvar-hr`/`urvar-erp`/`urvar-website`) — all managed by **PM2**, not Windows services or WinSW. `D:\urvar-crm\ecosystem.config.js` defines the `urvar-crm` PM2 process (`next start -p 3002`, matching the sibling apps' `next start -p <port>` pattern — ports 3000/3001/3002/3003 are hr/erp/crm/website respectively). PM2 itself runs as an Automatic Windows service, so `pm2 save`d processes auto-resurrect on reboot; after a reboot, `pm2 list` should already show `urvar-crm` as `online` without manual intervention. Cloudflare Tunnel routing (`crm.urvarindia.com` → `localhost:3002`) is its own separate Windows service, `CloudflaredCRM` (config at `C:\Windows\System32\config\systemprofile\.cloudflared\urvar-crm-config.yml`, tunnel id `d16dcb83-1033-47c5-b4f4-2fd18ae683b5` — a tunnel that had existed on the Cloudflare account since 2026-06-26 but was never wired up until this deploy), mirroring the sibling `Cloudflared`/`CloudflaredERP`/`CloudflaredWebsite` services exactly (each is a raw Windows service whose binary path directly invokes `cloudflared.exe --config=<path> tunnel run`, not `cloudflared service install`). **No nightly DB backup is currently configured** — the previously-documented `UrvarCrmPgBackup` task and `E:\UrvarCrmBackups` never actually existed. To ship a new build to prod: `npm run db:generate && npx prisma migrate deploy && npm run build && pm2 restart urvar-crm` — **no elevated shell needed** for this (a genuine improvement over the old fictional WinSW flow); elevation is only needed for Cloudflare Tunnel service changes (rare, one-time setup already done).
- **Call recordings require `<Record>`'s `callbackUrl`, not just `action`.** With `startOnDialAnswer: "true"` (used since `<Record>` is a sibling of `<Dial>`, not nested), Plivo sends the initial `RecordingDuration: "-1"` ping to `action` but delivers the **real** completion payload (actual `RecordUrl`/`RecordingID`/duration) only to `callbackUrl` — a gap missed during the original Twilio→Plivo port, so real calls connected fine but recordings never appeared (confirmed via a direct DB check: a genuinely-connected call had `recordingUrl`/`recordingSid` both null, not even the raw-URL fallback a failed download would leave). Fixed in `src/app/api/voice/plivo/answer/route.ts`'s `addRecord({...})` call by setting `callbackUrl`/`callbackMethod: "POST"` to the same `/api/voice/plivo/recording?callId=...` endpoint already used for `action`. While in that code, also hardened `src/app/api/voice/plivo/recording/route.ts` to leave `recordingUrl`/`recordingSid` `null` on a failed local download instead of silently falling back to the raw external Plivo URL (which the UI's `startsWith("/api/voice/recordings/")` check would then hide with no visible error), and fixed `src/lib/call-recordings.ts` to strip a trailing query string before checking/appending the `.mp3` extension. Not yet live-verified end-to-end with a real call against this fix — do that before assuming it's fully resolved.
- **`CloudflaredCRM` now has crash-recovery configured, matching its siblings.** On 2026-09-08 a reboot crashed all four cloudflared-family services simultaneously; `Cloudflared`/`CloudflaredERP`/`CloudflaredWebsite` auto-restarted (they had `sc.exe qfailure` → `FAILURE_ACTIONS: RESTART -- Delay = 20000 milliseconds`, `RESET_PERIOD: 86400` configured from their original setup) but `CloudflaredCRM` had no failure action at all — it stayed down and crm.urvarindia.com served a Cloudflare 1033 error until manually restarted. Fixed with `sc.exe failure CloudflaredCRM reset= 86400 actions= restart/20000` to match the other three exactly, then verified by force-killing the process and confirming it auto-restarts within ~20s (event ID 7031 in the System log, `Service Control Manager` source). If a fresh Cloudflare Tunnel service is ever created for another app on this box (following the pattern in the bullet above), set this failure action on it too — `New-Service`/`sc.exe create` doesn't configure it by default.
- **No automated test suite.** Validate changes with `npm run lint` and `npm run build` (type-checks via `tsc`), plus manual testing through `npm run dev`. Targeted harnesses exist for the voice agent: `npm run eval:agent` replays 21 scripted multi-turn calls across Bengali/Hindi/English (was 6, Bengali-only, against a prompt with no catalogue loaded — its price assertions used to pass for the wrong reason) through the real system prompt and CRM tool schemas (tool execution stubbed — it never writes to the DB), scores both LLM providers, and exits non-zero on any failed check so it can gate a deploy (`EVAL_REPORT=path.json` for a machine-readable report). A provider timeout now counts as a stall, not a failed check — a run once reported a 3x TTFT difference as "7/9 checks" when the provider had actually just been unreachable for a third of the scenarios. `npm run voice:stats` measures how the agent actually talks (turn length, question-stacking, talk ratio) from stored transcripts, and `npm run voice:latency` summarizes the `[turn]`/`[call-metrics]` telemetry lines into p50/p90. `npm run tts:samples` renders the same line across speakers/pace/preprocessing into `storage/voice-samples/` for a human to listen to. Run `eval:agent` after any change to the agent prompt or tools.
- **`prisma migrate dev` does not work on this box** — the DB user lacks `CREATE DATABASE`, so the shadow database fails with `P3014`. On a database that *is* production, that's a feature rather than a problem. To add a migration: edit `schema.prisma`, run `npx prisma migrate status` (confirm no drift), generate the SQL with `npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script -o prisma/migrations/<timestamp>_<name>/migration.sql`, **read it and confirm it contains no `DROP`/`TRUNCATE`**, then apply with `npx prisma migrate deploy` and `npm run db:generate`. Note the flag names: `--from-schema-datasource` was removed in Prisma 7 in favour of `--from-config-datasource`.
- **Better-auth user email/password are edited directly via Prisma, not the admin plugin.** `src/app/(dashboard)/users/actions.ts` updates `User.email` directly and, for password resets, hashes the new password with `hashPassword` from `better-auth/crypto` and writes it to the user's `Account` row (`providerId: "credential"`, upserted) — this matches what better-auth's own `admin.setUserPassword` endpoint does internally, without pulling in the full `admin` plugin (which would require mapping our 5-role RBAC onto better-auth's own role/permission system). Never log the plaintext password to the audit trail — log a `passwordChanged: true` flag instead.

It's mirrored at `src/app/icon.png` (Next.js app-icon convention) and baked into `src/app/favicon.ico` as a hand-built multi-size ICO (16/32/48px, generated via `sharp` since no PNG→ICO CLI was on this box — see git history for the one-off script). If Urvar ever issues a brand refresh, re-pull from `urvarindia.com` (their CDN 403s a bare `WebFetch`/no-UA request — use `curl` with a real browser `User-Agent` string) — the full vertical wordmark lockup is at `/logo.png` and `/logo.svg` there, distinct from the square icon.

Run `npx prisma migrate status` before `prisma migrate dev` to confirm there's no drift (a drift-triggered reset prompt would wipe production data); additive nullable-column migrations are low-risk but still real production schema changes, not throwaway dev ones.
- **Local dev on this box can't use ports 3000-3003 or a `.env.local` file.** Those four ports are taken by the four PM2-hosted apps (hr/erp/crm/website) — run `next dev` on something else (e.g. `PORT=3005`, the port used for this repo's own live-call testing). `.env`'s `NEXT_PUBLIC_APP_URL`/`BETTER_AUTH_URL` are hardcoded to `https://crm.urvarindia.com`, so better-auth's client will try to hit production unless overridden — pass `NEXT_PUBLIC_APP_URL`/`BETTER_AUTH_URL` as shell env vars on the `npm run dev` command itself (they take precedence over `.env`). Don't create a `.env.local` to do this instead: the `urvar-crm` PM2 process runs `next start` from this exact same `D:\urvar-crm` working directory, so a stray `.env.local` would silently override production's auth URLs on its next restart too. Also stop the local dev server before running `npm run build` for a real deploy — `next dev` and `next build` share the same `.next` directory and can conflict if run concurrently.
- **Customers can be pinned to an exact map location.** `Customer.latitude`/`longitude` (nullable `Float`) are set via a Leaflet + OpenStreetMap dialog (`customers/[customerId]/location-dialog.tsx` + `location-map.tsx`, dynamically imported with `ssr: false`) — no API key/billing since it's OSM tiles, not Google Maps. Includes a browser-geolocation "Use My Location" button with an accuracy-radius circle for field reps pinning a site in person.
- **Calling works from both Leads and Customers.** `initiateCall`/`logCall` (`src/app/(dashboard)/calls/voice-actions.ts`, `actions.ts`) take a `{ leadId } | { customerId }` discriminated union, not a bare id — `completeVoiceCall` already branched on `existing.leadId`/`existing.customerId` before this, so the two entry points were generalized to match that existing precedent rather than duplicated per entity. The `Call` model already had both FKs from the start; the global `/calls` list joins both `lead` and `customer` and links to whichever is set.
- **Calling has migrated from Twilio to Plivo** (Indian caller ID). Twilio was never actually live (all six `TWILIO_*` vars were blank placeholders) and its India KYC path was dropped in favor of Plivo's simpler self-serve flow. **Account-side**: Plivo KYC for "Urvar Natural" is Approved, a Bangalore Voice-capable number `+91 80 3190 3300` ("Urvar CRM Main Line") is purchased, and a Plivo Application ("Urvar_CRM_Voice", Answer URL `{APP_URL}/api/voice/plivo/answer`, Hangup URL `{APP_URL}/api/voice/plivo/status`) is created and linked to the number. `PLIVO_AUTH_ID`/`PLIVO_AUTH_TOKEN`/`PLIVO_APP_ID`/`PLIVO_CALLER_ID`/`ENCRYPTION_KEY` are populated in `.env` (see `.env.example` for the blank-placeholder shape). **Code-side**: `src/lib/plivo.ts` (replaces `twilio.ts`), `src/app/api/voice/plivo/{answer,status,recording}/route.ts` (replace `twiml`/`status`/`recording`), `src/lib/call-recordings.ts`, `src/lib/crypto.ts` (new — AES-256-GCM at-rest encryption via `ENCRYPTION_KEY`), and `CallProvider.tsx` (now `plivo-browser-sdk`'s `Client`, event-driven not per-call-object like Twilio's `Device`) are all rewritten; `npm run lint` and `npm run build` pass. Per-user Plivo SIP **Endpoint** credentials (`User.plivoEndpointId`/`plivoUsername`/`plivoPasswordEncrypted`) are created lazily on first call and are persistent (unlike Twilio's ephemeral ~1hr AccessToken) — password encrypted at rest via `src/lib/crypto.ts`. `CallProvider` enum gained `PLIVO` (kept `TWILIO` — historical rows still reference it). **Live-tested end-to-end** (2026-09-08, dev server on port 3005 + a temporary `cloudflared tunnel --url` pointed at the Plivo Application's Answer/Hangup URLs, reverted back to `crm.urvarindia.com` after): Endpoint creation, SIP login, `client.call()`, the `answer_url` webhook, `<Dial>`+sibling `<Record>` XML, and the hangup/status webhook all confirmed working against real Plivo payloads, with the `Call` row (`providerCallSid`, `toNumber`, `providerStatus`, `durationSeconds`) updating correctly. Bugs found and fixed during that test: (1) Plivo Endpoint `alias` rejects spaces — use `.`/`+`/`@`/`-`/`_` only; (2) Endpoint `username` must be ≤25 chars, strictly alphanumeric (no underscore) — our 32-char Better Auth user ids are hashed down via `sha256(...).slice(0,24)` in `getOrCreateEndpoint`, not used raw; (3) Plivo can silently mangle a requested username — always store `created.username` from the API response, never the locally-generated value; (4) the Dial-level status callback (the one carrying our `callId`) uses `DialBLegStatus`/`DialBLegDuration`, **not** `CallStatus`/`CallDuration` (those only exist on the separate Application-level Hangup URL hit, which has no `callId` and is correctly 400'd) — `src/app/api/voice/plivo/status/route.ts` reads the right fields now; (5) `plivo-browser-sdk` references `window` at module load, so `CallProvider.tsx` must dynamic-`import()` it inside the client-only `useEffect`, never as a static top-level import, or SSR crashes with "window is not defined". Also confirmed empirically: an Endpoint-originated call's `Direction`/`CallDirection` reports `"inbound"` (the documented Plivo quirk) — don't gate authorization on it, as this code already doesn't. Recording download Basic Auth is still **off by default** in Plivo — enable Console > Voice > Other Voice Settings > "Basic Auth For Recording URLs" before relying on it being enforced. The Plivo account is still on a **Free Trial**; the test call above worked on it, but confirm before assuming no further limits apply at higher volume. Now that `crm.urvarindia.com` is genuinely deployed (PM2 + `CloudflaredCRM`, see below), Plivo's Answer/Hangup URLs need no further tunnel workaround — they already point at the real domain.
- **The AI voice agent's conversation LLM is provider-swappable.** `voice-agent/pipeline/llm-provider.ts` is the only place that knows how the two providers differ, and every difference was established by probing the live APIs, not from docs: Sarvam authenticates with an `api-subscription-key` **header** (not a bearer token) at `https://api.sarvam.ai/v1`; `reasoning_effort: "none"` is OpenAI-only and Sarvam rejects it (`Input should be 'low', 'medium' or 'high'`); OpenAI's current models reject `max_tokens` and require `max_completion_tokens` while Sarvam wants `max_tokens`. Switch with `VOICE_AGENT_LLM_PROVIDER=openai|sarvam` plus `pm2 restart urvar-voice-agent` — no rebuild, revert in seconds. `sarvam-105b-conversations` is **currently live** after a measured pilot: median TTFT ~400ms vs gpt-5.4's ~1090ms (~3x faster to first word), scoring 16-17/18 on `npm run eval:agent` against the incumbent's 18/18. Two portability bugs it exposed, both since fixed: the farewell completion must send `tools` even though it needs none (Sarvam 400s on tool history with no tool definitions, OpenAI tolerates it), and a lead utterance arriving mid-generation used to be **dropped** rather than queued.
- **Voice-agent conversation quality is mostly prompt and pacing, not the model.** Hard-won specifics, each from a real failed call: `clearAudio` must fire only on a genuine barge-in — sending it on every transcript truncates the AI's own sentence, which made it re-introduce itself four times in one call; short backchannels ("haan", "hello", "bataiye" — see `pipeline/backchannel.ts`) are ignored while it is speaking, and that matcher must keep `\p{M}` when stripping punctuation or every Bengali/Devanagari entry silently fails to match. TTS is sentence-chunked, never clause-chunked: an earlier eager comma-split was the actual cause of a "robotic" complaint, because each fragment got its own sentence-final intonation. Sarvam TTS needs `speech_sample_rate` (not `target_sample_rate` — a wrong key is silently ignored and you get the 24kHz default), `language_code` is required and has no "auto", and an explicit `flush` after the last utterance of a turn. Because `end_call` compliance is unreliable on *both* providers, `server.ts` also enforces server-side wrap-up: 15s silence and a 5-minute cap.
- **Sarvam document intelligence (`src/lib/sarvam-vision.ts`) powers all document intake.** Use the **extract** endpoint (`POST /doc-ai/v1/job/extract`), not digitise: extract returns structured field values, digitise returns a ZIP of Markdown you would then have to parse. It is a job queue — submit, poll `/job/<id>/status`, fetch `/job/<id>/results`. The `schema` field must be a real **JSON Schema** object (`{type:"object",properties:{field:{type:"string",description:"..."}}}`); a plain `{field: description}` map is rejected with `SCHEMA_INVALID: schema property contains unsupported key "..."`, which misleadingly reads like a problem with the field name. Hard limits on **every** tier including Enterprise: 10 requests/minute, 10 pages per PDF, 200 MB — so bulk backfills are impossible and the UI is one document at a time by design.
- **Uploaded documents follow the call-recording storage pattern.** `src/lib/documents.ts` writes to `DOCUMENTS_DIR` (default `./storage/documents`) naming each file by its `File` row cuid — never by the user-supplied filename, so a crafted name cannot escape the directory — and `src/app/api/documents/[fileId]/route.ts` authorises the **database row** (via `scopeWhere` on the related lead/customer/quotation/purchase-invoice) before reading any bytes. That route is **deny-by-default**: a `File` attached to nothing matches no branch and is refused. The previously-dead `File` model is now live. Note the existing spreadsheet import route still validates by filename extension only and checks neither size nor MIME; `assertUploadAllowed` does both.
- **Extraction never writes to a record directly.** Lead capture from a document (`leads/import`) converges on the *existing* spreadsheet importer — fields are requested under the importer's own names so the column mapping is the identity map, and `validateImportRows`/`commitImport` then give documents the same duplicate-phone detection and Zod validation for free. Attach-and-extract on a lead (`leads/[leadId]/document-actions.ts`) proposes changes the rep ticks, with `name`/`phone` deliberately **not** extractable (overwriting them could repoint a record at a different person) and the accepted payload filtered against a server-side whitelist rather than trusted. Models answer "N/A"/"not mentioned" instead of omitting a blank field, so those placeholders are stripped or they pass validation as real values.
- **Procurement (`/purchases`) is the only inbound side of the schema.** `Supplier` / `PurchaseInvoice` / `PurchaseInvoiceItem` exist so a scanned supplier invoice has somewhere to land; everything else in the CRM is outbound (`Quotation → Order`). `PurchaseInvoiceItem.productId` is **optional**, unlike `QuotationItem.productId` — a supplier lists what they sell, so forcing a catalogue match would make some invoices impossible to record. The `purchases` module is `NONE` for all three sales roles and full only for `SUPER_ADMIN`/`ACCOUNTS_TEAM`, because supplier prices reveal the margin on every deal; `/api/documents` gates invoice scans on that same module so a rep who can read leads still cannot open one. `@@unique([supplierId, invoiceNumber])` catches the same invoice being photographed twice, and suppliers are matched by name before a new one is created.
- **Fixed: the territory-scope RBAC hole, and a second one found while fixing it.** `leads/page.tsx`, `customers/page.tsx` and `customers/distributors/page.tsx` used to spread `scopeWhere(...)` and *then* set `where.state = params.state`, which silently overwrote the territory restriction — plain JS object-key collision, nothing to do with Prisma. Verified against real data before fixing: a `DISTRIBUTOR_MANAGER`-shaped query leaked **17 out-of-territory leads** via `?state=`. The same collision existed for `own` scope on `assignedToId` — a `SALES_EXECUTIVE` could read **another rep's leads** via `?assignedToId=<their-id>` even though the UI never renders that control for `own` scope, because the page still read the raw query param; confirmed leaking 6 rows. Both are fixed the same way: `where = { AND: [scopeWhere(...), filters] }` instead of a spread — Prisma ANDs duplicate keys across array elements rather than one overwriting the other, so a conflicting param now returns zero rows instead of the wrong ones. Re-verified after the fix: both leaks blocked to 0, legitimate in-territory/in-scope filtering unaffected. Apply the same `AND` pattern to any future page that combines `scopeWhere()` with request-controlled filters.

- **Fixed: AI calls that connected but recorded no outcome, and a transcript a slow summarizer could destroy.** `end_call` was the only thing that ever wrote `Call.outcome`, and its own reliability is unmeasured — confirmed, 9 of 20 real `AI_AUTONOMOUS` conversations ended with a full transcript and no outcome and nothing for a rep to follow up on, including a 122-second call where the lead had confirmed interest. `voice-agent/server.ts`'s `finalizeSession` now records a default outcome (`CONNECTED`, or `TRANSFERRED_TO_HUMAN` after a handoff) plus a follow-up task whenever `end_call` never fired, via a new `recordCallOutcome()` shared with the tool's own `end_call` branch (`voice-agent/tools/crm-tools.ts`) so the existing P2002-on-duplicate-`FollowUp` guard can't drift between the two call sites. Separately, `transcript` and the OpenAI summary used to be written in one `prisma.call.update`; a summarizer timeout discarded the transcript along with it — the transcript's only copy, since the session is dropped right after `finalizeSession` returns. The two writes are now independent, so a failed summary costs only the summary.
- **Voice-agent quality audit (2026-09-11/12): measured before touching anything, not by feel.** There was zero latency instrumentation in production — the only number anywhere came from the offline `eval:agent` script. `voice-agent/pipeline/turn-metrics.ts` now emits one logfmt `[turn]` line per turn and one `[call-metrics]` line per call (`npm run voice:latency` summarizes them; PM2 has no `time:true` configured, so each line self-timestamps). Measured budget for a normal turn: ~1.5-1.8s, of which the single largest addressable cost (~470ms) turned out to be our own `MIN_SPEAK_CHARS` sentence-chunking rule waiting for the model to finish a long sentence — not the model (TTFT ~430ms) or TTS (~230ms; an immediate `flush` measured no difference — 222/220/244ms without it vs 228/238ms with — don't retry that idea). Across 103 real AI turns the agent averaged 19.4 words and did 76% of the talking (`npm run voice:stats` reproduces this from stored transcripts); the prompt in `pipeline/openai-agent.ts` now caps turns at 5-15 words with a short first sentence and one question at a time, which is simultaneously the biggest latency fix and the biggest naturalness fix. Barge-in used to wait for Sarvam's *final* transcript (300ms of silence after the lead stops talking), so a 2-second interruption got talked over for 2.3s — `vad.speech_start` was already arriving and being discarded. It's now two-stage: hold new TTS audio on speech onset, commit (send `clearAudio`, cancel the turn) once a partial transcript proves it's real speech, resume the held audio intact if it was noise or a backchannel. Revert with `VOICE_AGENT_BARGE_IN=final-only` + `pm2 restart urvar-voice-agent`. Three defects found while building it, all fixed: audio for a *cancelled* sentence kept streaming to Plivo after `clearAudio` (added a `routeTtsChunk` gate with a discard window); Plivo negotiates the outbound track even though the XML asks for inbound only, so the agent's own voice was being fed back into its own speech recognizer — harmless while barge-in waited for a final transcript, fatal once VAD drives it, since it would self-interrupt forever (now filtered); the holding-line apology bypassed the new gate entirely (now routed through `speakWithCheckpoint` like every other utterance). Full detail, scorecard and roadmap: `docs/VOICE_ARCHITECTURE.md`, `docs/VOICE_QUALITY_AUDIT.md`, `docs/VOICE_PERSONA.md`, `docs/VOICE_CONVERSATION_DESIGN.md`, `docs/VOICE_TEST_PLAN.md`, `docs/VOICE_OPTIMIZATION_ROADMAP.md`.
- **The product catalogue was one row with no price, and `transfer_to_human` was fully implemented but unreachable.** Live DB had exactly one `Product` (`Enriched Vermicompost`, `mrp: 0`), no dosage/crop/nutrient columns at all, and `get_product_info` matched names in English only — so a price question, or a Bengali "কেঁচো সার", found nothing, and the agent correctly refused to invent an answer but had nothing real to say either. `Product` gained 8 nullable agronomy columns (`targetCrops`, `problemSolved`, `dosage`, `applicationMethod`, `nutrientContent`, `benefits`, `objectionNotes`, `availability`) plus an "Agronomy details" section in `products/product-form-dialog.tsx` for Urvar's own team to fill in — **nothing agronomic was invented here**; a blank field makes the agent offer a callback instead of guessing, which is correct behaviour but not a substitute for real data, and it is still the hardest remaining limit on sales quality. The whole catalogue is now preloaded into the system prompt at call start (`voice-agent/server.ts`'s `handlePlivoStream`) instead of fetched mid-call — measured, a price question used to cost a full tool round trip and return a tool call carrying one character of prose, making the highest-intent moment in the call also the slowest. Separately: `transfer_to_human`'s Plivo route (`api/voice/plivo/transfer/route.ts`) and its tool-execution case always worked, but the tool schema was **never added to `CRM_TOOLS`** — the model could not call it no matter what the prompt said, ever since it was deliberately withdrawn on 2026-09-10 after a lead was told "connecting you now" and left holding when the transfer never actually happened.
